# Карта приоритетов: решения

Что это: журнал решений по прототипу отчёта, чтобы их не переоткрывали заново. Для передачи
Егору на доработку. Подробный ход работы и все найденные по дороге ошибки — в `NOTES.md`,
разбор его пакета — в `REVIEW-promo-platform.md` и `REVIEW-vocabulary-and-ux.md`.

**Итоговый файл — `priorities/index.html`.** Один файл, восемь экранов, без сборки и без
сервера: открывается двойным щелчком и работает без сети. Шрифт вшит внутрь.

**PDF не придуман.** Печатная раскладка сознательно не сделана: сначала должна устояться форма
основной страницы. В `@media print` лежит минимум, чтобы страница печаталась читаемо — это не
дизайн pdf, а заглушка. Двухстраничный pdf из `reportcontract.json` (executive summary +
детали) остаётся задачей, и делать его надо от готовой html-формы, а не параллельно.

---

## 1. Рамка

| Решение | Почему |
|---|---|
| Отчёт служит двум задачам лидера: разобраться, что со стратегией в команде, и купить stratos или imperfect | Всё остальное в отчёте — служебное. Если строка не работает ни на одну из двух задач, её нет |
| Рамка — «синхронизация в понимании стратегии, а не людей» | Формулировка владельца. Не «дошли ли приоритеты»: та ставит вопрос о людях |
| Слово «замер» из продукта изъято | «Мы не кухни продаём». В методике оставить можно |
| Слово «блок» — внутреннее, на экран не выходит | Читателю не нужно знать нашу структуру |
| Контейнер анкеты называется «анкета» | Выбор владельца из «сверка / тест / без слова» |
| До 20 ответов на экране счёт, от 21 — процент | «5 из 11» руководитель держит в голове и проверяет глазами. На 74 человеках он управляет массой, и «61 из 74» читается как «понятно, что много», а 82% — измеримо. Счёт уходит во вторую строку как проверка |
| Счёт остаётся там, где числа маленькие: панели по темам, приложение | «3 из 74» честнее, чем «4%» |
| Нейминг отвечает на боль лидера, а не описывает наши данные | Отсюда «Разобрать на встрече», а не «Низкие показатели» |

## 2. Визуальная система

Взята от «Искры», не от прототипов Егора. Отклонения от брендбука названы вслух в `NOTES.md`.

| Решение | Почему |
|---|---|
| Вермилион вместо голубого | Это промо-инструмент, а не внутренний продукт |
| Вермилион — заливки и крупные цифры; в тексте `#CC3700` | Белым по вермилиону было 3,40:1 — главная кнопка не проходила AA. Чернила по вермилиону дают 5,22:1 |
| Отдельные слова внутри фразы цветом и начертанием не выделяются | Правило брендбука. Пришлось снять подчёркивание в заголовке отчёта: оно рвалось на переносе |
| Шкала кегля — шесть ступеней, у каждой своя работа | Шестая (20px, заголовок вывода) добавлена сознательно: трёх уровней заголовков двумя ступенями не разложить |
| Один радиус 8px на всю платформу | |
| Заливка — подлежащее, контур — с чем сравниваем | Одно правило на все полосы и точки |
| Inter Tight вшит в файл (base64, два поднабора, ось веса 400–500, SIL OFL) | Без шрифта система подставляла свой, и раскладка выезжала там, где на другой машине сходилась |
| Полосы внутри панелей — графит, не чернила | Чернила — цвет текста; плотные чёрные полосы весили больше вывода, который их объясняет |
| Одна заливка на все полосы, без цветового кодирования | Было два цвета без написанного правила — прочитать его нельзя |

## 3. Архитектура отчёта

| Решение | Почему |
|---|---|
| Отчёт — заключение, а не дашборд: одна колонка чтения, 900px | Линейки разделов тянулись на 1325px в пустоту |
| Единица вывода: заголовок-вывод → объяснение одной фразой → окно результата | Слова ведут, числа следуют. Раньше это был список графиков с подписями |
| Девять выводов в трёх уровнях: разобрать на встрече / держать в виду / оставить как есть | Уровень отвечает на «что мне с этим делать» |
| Метка уровня — разделитель, а не заголовок: крупная цифра плюс прописная метка | Шла тем же кеглем, что заголовки под ней, и читалась как ещё один вывод |
| Верхняя группа ограничена четырьмя выводами | Повестка встречи на 15 минут не может быть из девяти пунктов. Остальные ниже порога уезжают в «держать в виду» с оговоркой, сколько их |
| «Оставить как есть» может быть пустым, и это пишется прямо | Прятать уровень нельзя: он часть механики |
| Окно результата 168×168 справа от текста, видно всегда, раскрывается при наведении | Раньше числа лежали в закрытом «показать цифры» — большинство читателей их не видело |
| Механика раскрытия — окно при наведении, не раскрытие на месте | Решение владельца. Раскрытие на месте лежит в истории git |
| Плюс в углу означает одно: за квадратом есть что смотреть. Не поворачивается | Поворот сообщал состояние, которого нет: на наведении окно уже открыто |
| Одна точка = один человек до 20 ответов, выше — полоса с долей | 74 точки — текстура, а не счёт |
| Приложение — отдельная страница, всегда с полным списком | Длинный список посреди документа сбивает чтение. Приложение «по условию» давало пустую страницу при заходе напрямую |
| В окне вердикта до восьми строк — все, дальше пять самых частых плюс ссылка | Измерено: панель нигде не выше 384px |
| Продажа — в одном месте, в конце, на плашке `--accent-tint` | Было три блока, два из них в середине без плашки читались как часть отчёта |
| Два набора продажных текстов: провал и сильная команда | «Стратегии пока нет» для сильной команды — ложь |
| «Что делать» — это предложение, а не плоские рекомендации | Требование Егора через владельца. Шаги «сделай сам» убраны |

## 4. Что надо поменять в методике (`SCORING.md`) — Егору

Это не вёрстка, это расхождения в самой модели. Найдены проверкой арифметики вручную и
прогоном девяти вариантов отчёта.

1. **Порог узкого места 7 → 8.** При семёрке 7³ = 343 < 500, поэтому «узких мест нет» и
   «заряда не хватает» могли напечататься вместе. Восемь по каждой шкале даёт 512, и
   противоречие снимается.
2. **Порог заряда 500 — очень высокая планка.** 500 в кубе — это 7,94, то есть «все три шкалы
   не ниже 8». Если одна шкала 6,0, двум остальным нужно по 9,13; если 5,0 — по 10,0, то есть
   невозможно. Реальный диапазон произведения примерно 150–700, и 500 стоит у верхнего края:
   «заряда не хватает» будет печататься почти всем. Три выхода: оставить и знать; опустить к
   343 («все три не ниже семи»); или заменить произведение на **минимум из трёх шкал** — он
   делает ту же работу (слабое звено решает), читается без порога и без шкалы 0–1000.
3. **S1 в фикстуре 3 считается от округлённых процентов** (88 вместо 87,5) — это нарушает
   правило самого файла.
4. **S2 — константа во всех фикстурах**, формулы нигде нет, а это 25% балла.
5. **`selfRatedClarity` 4,1** появляется в отчёте и в тексте наверх, формулы нет.
6. **Ресурсный конфликт** исключён из v1, но живёт в четырёх местах, включая пример вопроса.
7. **«Балл устойчив от 5 ответов» не работает на больших командах**: пять из 92 — не замер.
   Привязать к доле отклика, а не к абсолютному числу.
8. **Полосы оценок вывода: середина должна быть самой частой.** Пороги стояли у краёв, и
   уровень «держать в виду» почти не срабатывал. После расширения полос раскладка стала
   4/5/0 у слабой команды, 3/6/0 у средней, 0/0/9 у сильной. Конкретные пороги — в скрипте
   стенда, экран «варианты».
9. **Единицы меняются на 20 людях.** До двадцати ответов доля людей показывается счётом, от
   двадцати одного — процентом, счёт остаётся второй строкой. Это не оформление, а требование к
   контракту отчёта: обе формы должны приходить из модели.
10. **Что растёт с размером команды.** Список тем нельзя показывать счётом тем: 8 тем на 11
   человек и 23 на 74 несопоставимы. Считать **людей**: «34 из 74 работают над темами вне
   вашего списка». Дословные ответы, когда появятся, идут только в приложение.

## 5. Тексты

- Жёсткое правило: слова из методики не попадают в `COPY.md`. Таблица замен — в
  `REVIEW-vocabulary-and-ux.md`.
- Заголовки выводов говорят о передаче приоритетов, а не о людях.
- Подписи нейтральны по роду.
- Метки уровней параллельны по форме: «разобрать на встрече», «держать в виду», «оставить как
  есть» — все три про действие.

## 6. Открытые решения владельца

| Вопрос | Состояние |
|---|---|
| Порог заряда: 500, 343 или минимум из трёх шкал | Ждёт решения, см. 4.2 |
| Пороги и порядок трёх уровней вывода | Предложены, живут в стенде, в `SCORING.md` не перенесены |
| Название продукта: «карта приоритетов» или «карта futureproof» | Открыто |
| Что именно продаёт «Оценить стратегическое мышление» | imperfect — фасилитируемая диагностика на день; кнопка обещает меньше |
| Сентенс-кейс вместо строчных | Отклонение от брендбука, применено |
| Статистика «28% руководителей» снята с лендинга | Не было источника |
| Блок «Откуда эти данные» под баллом | Предложен, не сделан: отклик, независимость ответов, где ИИ и где арифметика, возможность прочитать ответы целиком |

## 7. Чего в прототипе нет

- **PDF.** См. начало файла.
- **Админка**: посмотреть ответы, дозаполнить отчёт, запросить консультацию.
- Экранов входа, писем, «отчёт закрыт», заявки на пилот, реферальной страницы.
- Юридических текстов.
- Логики: ничего не считается и не отправляется, все данные выдуманы.
- Экран «варианты» и экран «приложение» — служебные, в продукте их нет. «Варианты» нужен,
  чтобы проверять отчёт на разной силе и размере команды.

## 8. Развёртывание

Разворачивать **отдельно от «Искры»**: свой репозиторий, свой домен, своя база. Сейчас файл
лежит в `priorities/` внутри `imperfect-iskra-platform` только потому, что здесь ветка ревью.
Если оба продукта окажутся на `*.fproof.ru`, куки — без атрибута `Domain`.
